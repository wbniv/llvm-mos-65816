77524e40	body	Under +mos-a16 the accumulator is 16 bits, so codegen selects the Immediate16\naddressing mode -- a three-byte instruction -- but MOSInstPrinter printed its\noperand bare:\n\n    rep #32          ; M=0\n    adc #66          ; object: 69 42 00   reassembled: 69 42   (two bytes!)\n    sep #32\n\nThe assembler has no notion of the M/X flags, so `#66` always matches the\nnarrowest candidate (isImm8 is [0,255]). With M=0 the processor then consumes\nthe next opcode's first byte as the immediate's high byte and the instruction\nstream desynchronises from that point on. Values above 255 were safe by\naccident, which is why it went unnoticed. Reachable through plain -save-temps:\nno hand-written asm, no third-party assembler.\n\nThe sibling half of this defect -- 24-bit addresses printing bare -- was fixed\nin 0044; this is the same rule one width down, on the imm16 operand's\nPrintMethod. It is scoped to `def imm16` rather than the imm16at<> class, so\nimm16at5 (the HuC6280 tii/tdd block length, whose slot has no narrower sibling)\nstays bare.\n\nTwo corrections to the shape 0044's plan sketched for this item:\n\n  - The `<= 0xFF` threshold is not a guess. MOSDisassembler::getInstruction\n    already re-wraps a decoded Immediate16 operand in VK_IMM16 under exactly\n    that condition (<= UCHAR_MAX). A census over all 117 examples/65816\n    fixtures in both a16 modes found no negative immediate, none above 0xFFFF,\n    and no width modifier sitting on an Immediate16 operand -- the ambiguous\n    set is exactly plain constants in [0, 0xFF]. The printer handles the other\n    cases anyway: for an immediate, mos16() masking to the operand's width is\n    what encodeImm<Imm16> does regardless.\n\n  - The regression guard had to be a CodeGen test, not an 0044-style MC\n    round-trip one. llvm-mc -disassemble never enters M=0 (MLow comes from the\n    $ml/$mh mapping symbols, not from rep/sep bytes), so a raw byte list cannot\n    reach the three-byte form at all; and where it is reachable (llvm-objdump\n    over a real object) the disassembler has already wrapped the operand, so\n    such a test would pass before the fix. Only codegen produces a plain small\n    Immediate16 operand.\n\nDownstream-only, unlike 0044: upstream nothing constructs that MCInst, so this\npatch has no upstream target and queues no PR draft.\n\nVerified on the rebuilt toolchain: the new lit test fails pre-fix on three\nCHECK lines and passes post-fix; lit 159 discovered / 153 passed with the same\nfour known failures (no phw churn); dev/probe-far-roundtrip.sh over all 117\nfixtures goes 32 -> 0 divergent under +mos-a16 and is 0 divergent in all three\nmodes; corpus 80/80; corpus-a16 79/79, 0 xfail; an object built by the pre-fix\ndriver is byte-identical to the post-fix one; 0002 regenerates without\nabsorbing 0045.\n\nThe probe gained a --all flag, since its far/packed24 default corpus reached\nonly 2 of the 32 fixtures this defect touched.\n\nCo-Authored-By: Claude Opus 5 (1M context) <noreply@anthropic.com>\nClaude-Session: https://claude.ai/code/session_017sAprvTwtKFJHKgQmr1qgr
