# #120 — Bitboard Knight Tour (`bitboard64`)

**Status:** DONE + PUBLISHED 2026-08-03 — runnable positive plus two adjacent backend findings. Round 7 compiler-probe ROM.

## Question and shape

Can the target lower `__builtin_popcountll`, `__builtin_clzll`, and `__builtin_ctzll` on real
64-bit bitboards? Knight attacks use shift-and-mask bitboards; popcount scores reachability, ctz
chooses the next set square, and clz locates it from the opposite edge. A 96-step tour folds the
selected square, degree, leading-zero count, and visited mask into a CRC.

The board is the visual proof: the selected knight is gold, reachable squares pulse cyan, and
visited squares settle blue. These are the same bitboards used by the gate.

## Gates and published result

- Host oracle: `0xC074`.
- LLVM IR contains `ctpop.i64`, `cttz.i64`, and `ctlz.i64`.
- Contrary to the round plan's libcall prediction, MOS expands all three operations inline; the
  published form isolates each expansion in a noinline helper and passes `-verify-machineinstrs`.
- Host == default == a16 == xy16 == `0xC074` on MAME and bsnes-jg after 480 frames/ticks.

Run with `dev/run.sh bitboard64`.

## Findings retained from bring-up

1. Direct variable one-hot construction, `1ULL << uint8_t`, fails legalization at
   `G_ANYEXT s8 -> s64`. The published ROM uses a constant-shift loop. This is now direct evidence
   for #138 `shift64seam`, not a reason to hide or withdraw that probe.
2. Expanding ctpop/cttz/ctlz inline together inside the pressure-heavy tour step passes the LTO ROM
   build but fails an honest non-LTO `-verify-machineinstrs` object build with four undefined
   physical `__rc` uses. Splitting the three operations into noinline helpers removes the invalid
   live-range interaction. The helper boundary is a workaround, not the backend fix.

The runnable operation coverage is positive; both compiler defects remain follow-up work.
