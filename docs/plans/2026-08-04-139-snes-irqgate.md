# #139 — IRQ Gate (`irqgate`)

**Status:** implemented + verified 2026-08-04 — **clean positive**, `0x24F6`. Round 7, Cluster B.
**Plan item:** [Round 7 battery, Cluster B addendum #139](2026-08-03-round7-defect-hunting-demos.md).

## Question and shape

The first non-NMI hardware vector in this project ever to reach a C handler. crt0's weak
`irq: rti` stub is overridden by a real `__attribute__((interrupt))` handler driven by the PPU
V-count timer (`$4207–$420A` counts, `$4200` NMITIMEN enable, `$4211` TIMEUP ack), with the
v-blank NMI simultaneously live. Four things are asked at once:

- is the #123 width-safe envelope emitted on the **IRQ** path, not just the NMI path;
- can a C program run **CLI/SEI discipline** around an armed handler (crt0 masks IRQ at reset and
  nothing had ever unmasked it);
- does an **MMIO acknowledge** survive being written in C inside an ISR — `$4211` is read-to-clear,
  and a missed ack is an infinite re-entry, a hang no value gate can see;
- is the envelope **reentrant** when one interrupt lands inside another? Fully stack-based in
  principle, never proven.

**Determinism.** Both interrupts are asynchronous to the main loop, so each carries the #123
armed/done handshake with its *own* exact stop count — NMI at 120, IRQ at 96, deliberately
distinct so a handler wired to the wrong vector cannot land on the same pair. Each tally is folded
**independently** and the two folds are then combined, so the gate hash cannot depend on which
handler ran first or how they interleaved.

## Where the first design was wrong (and what measurement showed)

The original design set `VTIME = 224` — the last active scanline — reasoning that NMI fires at
v-blank (225) one scanline later, so a long IRQ handler body would still be executing and the NMI
would nest inside it. **It did not.** The gate ran deterministically in all three width modes but
returned `0x28F6` against a host oracle of `0x24F6`.

Probing the ROM's WRAM directly isolated it immediately: every component matched except one.

```
nmi_tally  got=0x0078   (120, matches host)
irq_tally  got=0x0060   (96,  matches host)
nmi_mix    got=0x13CFB8B3        (matches host)
irq_mix    got=0xDF7A14D8        (matches host)
nest_hits  got=0x0000   (expected 96)
```

So the interrupts, the tallies, the 32-bit handler arithmetic and the handshake were all correct
in every mode — only the *nesting* never happened. A second probe latched the PPU V counter at
each handler's entry (reading `$213F` first to reset the H/V latch flip-flop, then `$2137`, then
`$213D` twice — a single unreset `$213D` read alternates low/high byte and is what made the first
probe attempt return nonsense):

```
probe_nmi_v      = 0x00E2   (226)   NMI body reached at line 226
probe_irq_v      = 0x00E5   (229)   IRQ body reached at line 229
irq_in_nmi       = 0x0000           IRQ never landed inside NMI either
```

**A C interrupt handler's prologue is not free.** `irq` saves 26 imaginary registers, and the
measured latency from V-count trigger to the first line of the C body is ~5 scanlines. At
`VTIME = 224` the handler did not begin until scanline 229 — *after* the NMI it was meant to
catch. NMI's own prologue is shorter (9 `__rc` saves, ~1 line), which is why it measured 226.

This is a demo-design fault, not a compiler fault, and it is worth recording: any future raster-
timed work here must budget several scanlines for the C ISR prologue, and that budget scales with
how many imaginary registers the handler's body forces live.

**The fix is structural, not a retuned constant.** `VTIME` moved to 200, and the armed IRQ handler
now **rendezvous** with the NMI: having done its own work it spins until the NMI tally it sampled
at entry changes. NMI is non-maskable, so the I flag that IRQ entry set does not block it, and it
arrives every frame — the meeting is guaranteed by construction rather than by handler duration,
so it holds identically in default, a16 and xy16 despite their different code sizes. The spin is
bounded (`IRQGATE_SPIN_LIMIT`) so a pathological run yields a wrong CRC rather than a hung ROM.
Nesting is therefore *asserted in the differential* (`nest_hits == 96` folded into the hash), not
left as an exposure-based leg like #124's landing windows.

## What was built

- `examples/65816/irqgate.h` — shared model: separate NMI/IRQ step functions, independent folds
  combined at the end, the stop counts, `IRQGATE_VTIME`, and `IRQGATE_NEST_EXPECT`.
- `tools/irqgate-sim.c` — host oracle, prints the greppable `gate_crc = 0x%04X`.
- `examples/snes/irqgate.c` — C `interrupt, noinline` handlers `nmi` and `irq`; the IRQ handler
  does 12 rounds of 32-bit rotate/xor/add, rendezvous with the NMI, then acknowledges TIMEUP.
  `cpu_cli()` / `cpu_sei()` are inline-asm one-liners, unmasking only *after* both handlers are
  armed and re-masking before the snapshots are read.
- `dev/irqgate.sh` — the gate, cloned from the #140 hardening.
- `tools/nmitally-isr-gate.py` — one-line-scoped fix, see below.

### Shared-tool fix: a false positive in the C0 soft-stack check

`nmitally-isr-gate.py --symbol irq` initially reported

```
    FAIL  C0 soft-stack ptr: __rc0/__rc1 adjustments sum to 0x0019, not 0 (__rc0+230 __rc1+254 __rc0+25 __rc1+0 __rc0+26 __rc1+1)
```

The disassembly shows this is **not** a stack imbalance:

```
    82f9: a5 00   lda $0      ; <__rc0>
    82fb: 69 19   adc #$19
    82fd: 85 02   sta $2      ; <__rc2>      <-- destination is __rc2, not __rc0
    82ff: a5 01   lda $1      ; <__rc1>
    8301: 69 00   adc #$0
    8303: 85 03   sta $3      ; <__rc3>
    8305: 68      pla
    8306: 92 02   sta ($2)                   <-- ...it is a FRAME-SLOT POINTER
```

That sequence computes `__rc0 + 25` into `__rc2/__rc3` to address the handler's frame-resident
`volatile uint8_t ack` local — an address computation, not a soft-stack-pointer adjustment. The
gate's regex matched `lda __rc0; adc #imm` without checking where the result was stored. The real
carve/restore pair is `−282` at entry and `+282` at exit, which balances exactly.

The check now additionally requires the result to be stored **back to the same** `__rc` register.
This is strictly tightening — a genuine carve or restore always stores back — and it leaves #123
`nmitally` and #140 `brkcop` passing unchanged (both re-run and confirmed). Without it the gate
would mis-flag any ISR holding a frame-resident local, which #141 `dpbank` is likely to do too.

## Result

**Clean positive.** No compiler finding. The interrupt envelope is emitted correctly on the IRQ
path, the envelope is reentrant under NMI-inside-IRQ nesting (96/96 nests), the MMIO acknowledge
survives, and CLI/SEI from C behaves.

- Host oracle `0x24F6` (NMI 120 / mix `0x13CFB8B3`, IRQ 96 / mix `0xDF7A14D8`, nests 96).
- `host == default == +mos-a16 == +mos-xy16 == 0x24F6` on bsnes-jg; a16 3× byte-deterministic.
- MAME leg SKIP-by-design (no SPC700 IPL locally).
