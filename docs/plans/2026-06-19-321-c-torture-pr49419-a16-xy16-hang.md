## The test + symptom

[`pr49419.c`](../../vendor/c-torture/execute/pr49419.c): a global `struct S { int w, x, y; } *t`, walked as a
linked list through two loops:
```c
for (x = n, i = 0; t[x].w == f && i < m; i++) x = t[x].x;   // loop1
...
for (x = n; i > 0; i--) { s[i] = t[x].y; x = t[x].x; }       // loop2
```
At runtime (`n=0,f=1,m=3`, `buf={{1,1,2},{0,0,0},{0,0,0}}`) `foo` must return 2 with `s[0]=1, s[1]=2`.

- **Symptom:** `+mos-a16` **and** `+mos-xy16` → `corpus_result == 0x0000` (the test never writes the PASS/FAIL
  sentinel → a **hang / infinite loop**, not a wrong-value `0xDEAD`). DEFAULT is correct. a16+xy16 both fail
  ⇒ a **shared a16-path** bug (xy16 implies a16), not xy16-index-specific.
- Still fails after the frame-index fix + dg-require refinement (confirmed in the class sweep).

## Findings so far

- **Loop1** (`LBB0_2`, rotated): computes `newx = t[x].x` then tests `t[newx].w == 1` (next-iter check, hoisted)
  and `i < m` as `cpx #2` (correct for the rotated `i+1 < 3`). The continue flag threads through `Y`; exit is
  `inx; tya; beq`. **Traces as correct** on the runtime inputs (exits when `t[1].w != 1`). Not yet the suspect.
- **Loop2 / tail** (`LBB0_13`): contains `cmp #32771` (= `cmp #(3 ^ 0x8000)`, the native **s16 signed-compare**
  idiom `eor #$8000; cmp #…` for a comparison against signed `3`) and a `jmp .LBB0_13` back-edge plus a
  `.LBB0_20: bra .LBB0_14` edge. Loop2's source condition is `i > 0` — a compare against **signed 3** here is
  unexpected and is the **prime suspect** for the non-terminating loop.
- The struct stride `*6` (3×`int`) is open-coded `asl`/`asl;asl`/`adc` — looks fine.

## Hypotheses (to confirm / refute — cap at 3)

1. **Native s16 signed-compare lowering** miscompiles a loop bound (the `cmp #0x8003` against signed 3),
   leaving loop2 (or the `i==m` guard / `a=i+1` path) with a condition that never goes false → hang. Most
   likely given a16+xy16-shared + the hang symptom + the surprising constant.
2. **Loop-rotation / induction interaction** under a16 (the `i`/`x` SSA threaded through `Imag16`/`A16`)
   produces a back-edge that doesn't decrement/terminate.
3. **Struct-indexed load** (`t[x].x`/`t[x].w`) reads the wrong field, so the walk never reaches the
   terminating element.

## Update 2026-06-19 — narrowed to an xy16 flag/width bug (not instruction logic)

Traced the full xy16 `torture_test_main` and compared to the a16 (now-passing) build:
- **loop1** (xy16 `LBB0_6`): exit is `iny; txa; bne` — loops on the **continue flag in X** (not Y), `Y`=`i`.
  Traces correct (1 iter, `i`→1, exits when `t[1].w != 1`). Uses 16-bit-indexed `lda abs,x` (`rep #16; ldx;
  lda mos8(buf+off),x`) for `t[x].x` / `t[newx].w`, with `rep #16`/`sep #48` toggling the X (index) flag.
- **loop2** (xy16 `LBB0_14`): **byte-identical** to a16's `LBB0_13` (`lda rc4; eor #$8000; cmp #$8003; bcc`),
  `rc4`=`a`=`i+1`=2 → exits immediately. Correct.
- **final checks / loop2-skip** (`LBB0_15..LBB0_21`, `LBB0_21: bra LBB0_15`): terminate (rts/abort), no cycle.

So at the **instruction-logic** level every block is correct in xy16 too — yet it hangs. ⇒ the defect is in
the **processor flag state**, specifically the **X (index-register width) flag**: an index reg read/written
at the wrong width (8 vs 16) would corrupt a pointer/loop-var at runtime → a loop that never terminates,
invisible to an instruction-by-instruction read. This is the **`MOSInsertREPSEP` X-flag lattice** — the
xy16-only addition (a16 keeps the index 8-bit and emits no `rep #16`/`sep #16`/`sep #48`, so it's immune).

**Next step:** dump MIR after `mos-insert-rep-sep` for the xy16 build and check the X-flag mode at each
`lda abs,x` / `ldx`/`txa`/`iny` against the actual `rep #16`/`sep #16`/`sep #48` placement (find a block
entered with the X flag in the wrong state). Likely **shared** with `k_isort`/`doloop-1`/`20041011-1` (all
xy16) — fixing the X-flag lattice could clear several at once (as the a16 frame-index fix cleared 13).
