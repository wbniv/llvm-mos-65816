## 1. What this increment is (and is not)

Phase 1 §6 constraint 3 names the **zero-proof sub-case** as Phase 2's first increment:

> The zero-/small-constant-displacement sub-case (`Y ∈ {0,1,2,3}`) **needs no proof** and is the
> highest-confidence, lowest-risk slice: it is a pure replacement of the `inc/bne` carry chain.

Read against §5.2, "zero-proof" means a **compile-time-constant** byte displacement off an
already-built runtime far pointer — the multi-byte access pattern (`uint16_t`/`uint32_t` element
read through a far pointer, struct field at a constant offset). It is **not** a runtime index
proven in range; that is the general range-gated case and is **out of scope here** (increment 2).

**Out of scope, explicitly:** runtime/variable indices, `+mos-xy16`-specific 16-bit index folding,
`9f` (`sta long,X`), and the long-form arithmetic (Phase 1 §6 constraint 6).

## 2. The defect being removed

Current codegen for `out = tbl[i0]` (far `uint16_t[]`, `volatile` index) — reduction compiled with
the shipped toolchain, `-mcpu=mosw65816 -Os +mos-a16`:

```
  3d: a7 00        lda [$0]          ; byte 0
  3f: e8           inx               ; ── +1 carried through all four pointer bytes
  40: d0 09        bne  4b
  42: c8           iny
  43: d0 06        bne  4b
  45: e6 00        inc  $0
  47: d0 02        bne  4b
  49: e6 00        inc  $0
  4b: 86 00        stx  $0           ; ── re-home X/Y into the Imag32 quad
  4d: 84 00        sty  $0
  4f: a6 00        ldx  $0
  51: 86 00        stx  $0
  53: a6 00        ldx  $0
  55: 86 00        stx  $0
  57: 85 00        sta  $0
  59: a7 00        lda [$0]          ; byte 1
```

26 bytes (`0x3f`–`0x58`) of pointer advance to reach the adjacent byte. The target shape is
`ldy #$01 ; lda [$0],y` — **4 bytes** — off the *same* Imag32 quad, which also frees a second quad.

Post-legalizer MIR confirms the shape (bottom-up legalization means the `G_PTR_ADD` is still
intact when the load is legalized — see §4 risk R1):

```
  %10:_(s8) = G_LOAD_FAR_INDIR %5:_(p2)        :: (load (s8) from %ir.2)
  ... G_PTRTOINT/G_UNMERGE/G_INC/G_MERGE/G_INTTOPTR ...
  %12:_(s8) = G_LOAD_FAR_INDIR %11:_(p2)       :: (load (s8) from %ir.2 + 1)
```

## 3. Design

### 3.1 Chosen approach — mirror the existing near-pointer `(dp),Y` path exactly

The 16-bit-pointer legalizer already does precisely this job for `lda (zp),y`
(`MOSLegalizerInfo::selectIndirectAddressing`): peel `G_PTR_ADD`s accumulating a constant, and if
the residual base is a runtime pointer with a constant offset in `[1,255]`, materialise the
constant into `Yc` and emit the indexed opcode. The far path gets the same three-layer treatment,
one layer per existing far counterpart:

| layer | existing (far, unindexed) | existing (near, indexed) | **new** |
|---|---|---|---|
| generic opcode | `G_LOAD_FAR_INDIR` / `G_STORE_FAR_INDIR` | `G_LOAD_INDIR_IDX` / `G_STORE_INDIR_IDX` | `G_LOAD_FAR_INDIR_IDX` / `G_STORE_FAR_INDIR_IDX` |
| legalizer | `tryFarIndirectAddressing` | `selectIndirectAddressing` | `tryFarIndirectIndexedAddressing` |
| pseudo | `LDIndirLong` / `STIndirLong` (`a7`/`87`) | `LDIndirIdx` / `STIndirIdx` | `LDIndirLongIdx` / `STIndirLongIdx` (`b7`/`97`) |

The MC-layer instructions **already exist** — `LDA_IndirectIndexedLong` / `STA_IndirectIndexedLong`
are generated by `CC1_NoImmediate`'s `_IndirectIndexedLong` under `HasW65816`. Nothing new is added
below the pseudo layer, so the assembler, disassembler and AsmPrinter are untouched.

**Rejected alternative:** a post-RA peephole in `MOSLateOptimization` that rewrites
`LDIndirLong` + a preceding `G_INC` quad into `LDIndirLongIdx`. Rejected because by post-RA the
pointer advance has already been *committed* to two distinct Imag32 quads and to X/Y residency
(the `stx/sty/ldx/stx` re-homing above); recovering the single-quad form means undoing register
allocation, and the peephole would have to prove the intermediate pointer value is dead. Doing it
at legalization — where the offset is still a `G_PTR_ADD` constant — is where the information is.

### 3.2 The gate (Phase 1 §6 constraints 1, 2, 4, 5)

`tryFarIndirectIndexedAddressing` fires **only** when every one of these holds; failing any one
falls through to `tryFarIndirectAddressing`, i.e. today's already-correct add + `lda [dp]`:

1. The pointer is a 32-bit far (AS2) pointer — guaranteed by the `case 32:` dispatch.
2. `tryFarAbsoluteAddressing` has already failed, so the residual base is **not** a
   constant/global/frame-index far address (absolute-long is smaller for those). Because
   `matchAbsoluteAddressing` peels constant `G_PTR_ADD`s itself, a global base can never reach
   here — the base is a genuine **runtime** far pointer, already destined for an Imag32 ZP quad
   (constraint: "far pointer already in a DP slot").
3. The displacement is accumulated by peeling `G_PTR_ADD`s whose offset is a **compile-time
   constant** (`getIConstantVRegValWithLookThrough`). The peel **stops** — it does not fail — at
   the first non-constant offset: that inner `G_PTR_ADD` *is* the runtime far pointer the access
   hangs off. `tbl[i]`'s high byte is `G_PTR_ADD(G_PTR_ADD(@tbl, i), 1)`, so failing there would
   miss the single most common customer. The variable part is never folded into `Y` — that is
   increment 2.
4. The accumulated displacement is in **`[1, 3]`** — `kMaxFarIndirIdxDisp = 3`, Phase 1 §6
   constraint 3's `Y ∈ {0,1,2,3}` slice. `0` is deliberately excluded: `lda [dp]` with no `Y` is
   already the optimal encoding for it, and `tryFarIndirectAddressing` emits exactly that.
   Negative displacements are excluded by the lower bound.
5. Because the displacement is a constant ≤ 3, it is **always** expressible in an 8-bit `Y`
   (Phase 1 §6 constraint 1: `Y`'s width is governed by `X`, and `0..3 ⊂ 0..255`). The emitted
   index is an `s8` constant — the identical mechanism the near-pointer path already uses for a
   constant `(zp),y` displacement under **all three** modes including `+mos-xy16`
   (`selectIndirectAddressing` takes its constant-offset branch with `Use16BitIdx == false`
   whenever the offset is constant), so no new XY-width question is introduced.
6. Constraint 4, "`Y` free or already index-resident": handled by register allocation exactly as
   for the near-pointer constant-offset `(zp),y` form. Worst case RA inserts `phy`/`ply`
   (≈ 6 B / 11 cy, Phase 1 §5) against the ≥ 22 B this removes, so the worst case is still a win —
   no separate predicate is needed, and adding one could only cost wins.

Constraint 5 ("misclassification must only ever miss a win") is structural here: the function is a
pure `bool try…` that either rewrites the load/store or returns without touching it.

### 3.3 Correctness of the addressing mode itself

`[dp],Y` (`b7`/`97`) forms its effective address as *(the 24-bit pointer at `dp`) + Y*, and the
carry **propagates into the bank byte** — it does not wrap within the bank, unlike `(dp),Y`. That
is what makes it a semantically exact replacement for the 32-bit pointer add it replaces, including
across a `$xxFFFF → $xx+1:0000` boundary. This is the one hardware-semantics claim the change rests
on; §5 step 7 is the differential evidence for it.

## 4. Risks

- **R1 — legalization order.** The fold requires the `G_PTR_ADD` to still exist when the load is
  legalized. LLVM's `Legalizer` populates its worklist top-down per block and pops from the back
  ("perform legalization bottom up so we can DCE as we legalize"), so a load is legalized *before*
  the `G_PTR_ADD` defining its pointer. If that ever changed, the match would simply fail and we
  would fall back — a missed win, not a regression. **Evidence required:** the new lit test must
  actually show `b7`; a silent non-fire is a visible test failure, not a silent pass.
- **R2 — the `farindex` gate asserts `a7` is present.** The byte-0 load keeps `a7`; only the +1
  load becomes `b7`. The gate stays green, and a `b7` assertion is *added* as positive evidence.
- **R3 — a second Imag32 quad disappears.** The folded form keeps one quad live across both
  accesses rather than producing a second. That reduces ZP pressure (Phase 1 §3) but changes
  live ranges; `corpus`/`corpus-a16`/`fuzz` are the guard.

### The three-access cliff — a *separate*, reproducible defect

The fold always removes work: on the 3-access shape it deletes 11 `inc` + 9 `bne` (the carry
chains) and drops ZP use from 13 `__rc` bytes to 10. It regresses anyway because the **pre-RA
machine scheduler** flips to a schedule that interleaves the index-scaling shift chain with the
pointer-add chain, leaving **two carry (`Cc`) values live at once**. There is only one `P.C`, so the
second is materialised into a GPR — `ldy #1 / bcs +2 / ldy #0` to save (5 B) and `cpy #1` to
restore (2 B), twelve times:

```
bcs   6 ->  18 (+12)      inc  11 ->   0 (-11)
cpy   0 ->   9  (+9)      bne   9 ->   0  (-9)
ldy   7 ->  26 (+19)      inx   2 ->   0  (-2)
```

Disabling only that scheduler isolates it exactly:

```
3-access sum shape   -Os                        before= 397 after= 410 delta=+13
3-access sum shape   -Os -enable-misched=false  before= 369 after= 290 delta=-79
3-access rotate      -Os                        before= 412 after= 420 delta=+8
3-access rotate      -Os -enable-misched=false  before= 426 after= 340 delta=-86
(-enable-post-misched=false changes nothing: it is the PRE-RA scheduler.)
```

So the fold is worth **−79 / −86 bytes** on exactly the shapes that appear to regress, and the
scheduler is eating that and 80-odd bytes more. It is **pre-existing**, not created here: at
`-Os` the scheduler already costs the unmodified compiler 28 bytes on the same 3-access shape
(397 with misched vs 369 without). This change raises the pressure enough to cross its cliff.

**Disposition:** land the fold (it is correct, differential-green, and strictly removes
instructions and ZP bytes), and track the scheduler's carry-pressure behaviour as its own item.
Narrowing the gate cannot address it — no local, compile-time-visible predicate correlates with
"the scheduler will interleave two carry chains", and a fires-only-when-there-are-fewer-than-three
heuristic would be arbitrary and unmaintainable.

## 5b. Residual risk

- **Only the constant-displacement slice is covered.** The runtime-index case the investigation's
  §4 blit shape needs is untouched — measured unchanged (86 B before and after). That is
  increment 2, not a gap in this one.
- **The scheduler cliff is characterised but not fixed.** The mechanism is demonstrated
  (`-enable-misched=false` recovers −79/−86 B) but the fix is in `MOSMachineScheduler`'s
  carry-pressure model, a different subsystem. Until then, a function with three or more far
  multi-byte accesses is a few bytes larger than before.
- **`kMaxFarIndirIdxDisp = 3` is a measurement boundary, not a correctness one.** Nothing about
  4..255 is unsafe — `Y` is 8-bit under `X=1` either way — the cap just keeps this increment to
  the slice Phase 1 measured. Widening it is a one-line change plus its own measurement, and
  `far_load_indir_idx4` in the lit test pins the current boundary so the widening is visible.
- **No explicit 8-bit-value precondition.** `tryFarIndirectIndexedAddressing` lowers to
  `LDIndirLongIdx`/`STIndirLongIdx`, which are 8-bit-accumulator pseudos, and it does not assert
  that the mem-op is `s8`. Neither does `tryFarIndirectAddressing`, which it runs directly in
  front of and whose gate it strictly narrows — so any access this could take would otherwise have
  gone to the same 8-bit pseudo. The risk profile is therefore unchanged, but if a wider far
  mem-op ever reaches `selectAddressingMode`'s `case 32:`, **both** functions need the guard, not
  just this one.
- **The `0002` regeneration was run against two of another worker's *uncommitted* patches**
  (`0020`, `0033`), because the committed versions no longer reverse out of the shared `vendor/`
  tree. That is the same baseline `main`'s own dirty `0002` was generated on, so the result is
  consistent — but if their `0020`/`0033` changes are abandoned, `0002` will need a re-regen.
