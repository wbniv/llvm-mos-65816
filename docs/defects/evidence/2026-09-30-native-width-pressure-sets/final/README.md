With the flag off, the native classes still charge their low byte's generated sets, but no set is appended, `getNumRegPressureSets` returns the generated count, and no list carries an appended index. That is exactly the measured `memb1` variant.

## Why the gate is target-machine-wide, and read once

[`lto/find-setOptLevel.txt`](lto/find-setOptLevel.txt) holds the searches.

- `RegisterClassInfo` caches `PSetLimits` per register info (`RegisterClassInfo.cpp:116-136`, `RegisterClassInfo.h:171-173` at `06bc967d2668`). The pressure trackers size their tables from `getNumRegPressureSets`. The answer must therefore hold for the subtarget's lifetime, so a per-function gate is not sound.
- `TargetMachine::setOptLevel` has one caller in codegen: SelectionDAGISel's `OptLevelChanger` (`SelectionDAGISel.cpp:268,293`). It lowers the level while an `optnone` function is selected. MOS selects with GlobalISel, with aborts enabled and no SelectionDAG fallback (`MOSTargetMachine.cpp:113-115`), so that pass never runs. `LTOCodeGenerator`, `ThinLTOCodeGenerator` and the `llvm-lto` and `lto` tools set the level before the target machine exists. `vendor/llvm-mos` has the same callers.
- The constructor therefore reads the level once. The comment on it gives this reason, and reading it once keeps the set count fixed even if a later change adds a per-function level switch.

## Where the gate fires

- **`llc -O3`:** the lit test above, and the per-level measurements below, where every `-O3` row equals `memb1`.
- **`clang -O3` without LTO and an `-O3` LTO link:** confirmed with the downstream candidate toolchain ([Downstream](#downstream)); the split builds no clang.
- **The SDK's `-flto` link:** `mos-clang` passes `-plugin-opt=O<n>` to `ld.lld` only when an `-O` flag is on the link line ([`lto/driver-link-lines.txt`](lto/driver-link-lines.txt)). There is none without an `-O` flag, `O2` for `-Os`, `-Oz` and `-O2`, and `O3` for `-O3`. `ld.lld` sets the LTO codegen level to `clamp(lto-O, 2, 3)` (`lld/ELF/Driver.cpp:1532-1538`, `lld/Common/Args.cpp:22-24`), so only an `-O3` link codegens at `Aggressive`.
    - The SDK and the corpus and demo ROMs link without an `-O` flag or with `-Os`. The gate does not fire there, and they keep the appended sets. That is the accepted conservative outcome.
    - An `-O3` link codegens the whole merged module at `Aggressive`, including `MinSizeRel` library bitcode, so all of it runs without the appended sets.

## Downstream

The change was built into `vendor/llvm-mos` and measured there. It was **not landed**: see the finding below. `vendor/llvm-mos` was restored afterwards, and `0002` is unchanged. `dev/regen-patch.sh` regenerates origin's `0002`, and the rebuilt shared toolchain is bit-identical to the baseline: `llc` `f1fa50a2…`, `clang-23` `254624ba…`.

- **Adaptation.** The downstream LLVM has no `TargetRegisterInfo::getLargestRegClassForRegPressureSet`, so that override is left out. Everything else is the split's code ([`downstream/vendor-candidate.diff`](downstream/vendor-candidate.diff)).
- **Round trip.** `dev/regen-patch.sh` passed. The regenerated `0002` differed from origin's only in `MOSRegisterInfo.{cpp,h,td}`, `MOSSubtarget.cpp` and the two tests ([`downstream/0002-candidate-delta.diff`](downstream/0002-candidate-delta.diff)).
- **Tools.** The candidate tools are frozen in `build/pressure-sets/final/downstream/` ([`identity.sha256`](downstream/identity.sha256)): `llc` `9f9b74f9…`, `clang-23` `4c2d5ceb…` and `lld` `538a938b…`. The baseline is the far-prerequisite candidate `build/far-review-defects/candidate/llc` `f1fa50a2…`.
- **Suites.** MOS CodeGen and MC: 191 passed, 4 unsupported. The `-debug-only` gate test needs assertions and is unsupported in the Release toolchain. `native-width-default-pressure.ll` fails on the baseline and passes on the candidate ([`downstream/test-red-green.log`](downstream/test-red-green.log)).
- **`-verify-machineinstrs`.** On the fixed set, in native modes at `-O2` and `-O3`, the results are identical before and after. The only failures are the known lzss-gallery `record_result` "ran out of registers".
- **Differential.** `dev/run.sh corpus-a16` on the candidate toolchain passes 83 of 83: host == default == `+mos-a16` == `+mos-a16,+mos-xy16`, on MAME and on bsnes-jg. The SPC700 IPL is present, so no MAME leg was skipped ([`downstream/corpus-a16.log`](downstream/corpus-a16.log)). The candidate is correct. It is held only for its size effect.
- **Gate in real builds.** See [`lto/gate-real-builds.txt`](lto/gate-real-builds.txt), with nmitally at `+mos-a16`.
    - `clang -O3` without LTO gives exactly `llc -O3`'s code, which differs from `llc -O2`'s.
    - A `-flto -O3` link (`-plugin-opt=O3`) gives exactly `llc -O3` on its precodegen bitcode.
    - A `-flto -Os` link (`-plugin-opt=O2`) gives exactly `llc -O2`.
    - The baseline compiler's `-O2` and `-O3` code for the same inputs is identical, so the difference is the gate.
- **Finding: default-mode code grows downstream.** Codegen of the same frontend IR for 277 SNES corpus and demo sources at `-Os` ([`downstream/codegen-summary.txt`](downstream/codegen-summary.txt)):

    | Mode | Changed / identical / fail on both | Bytes before → after |
    |---|---|---|
    | default mosw65816 | 251 / 11 / 15 | 2,315,097 → 2,328,524 (**+13,427**, +0.58%; 207 larger, 35 smaller) |
    | `+mos-a16` | 168 / 108 / 1 | 2,441,232 → 2,444,235 (**+3,003**; 148 / 13) |
    | `+mos-a16,+mos-xy16` | 167 / 109 / 1 | 2,431,285 → 2,434,355 (**+3,070**; 143 / 12) |

    - The cause is the downstream computed-carry scheduling (`0064`/`0067`, default `-mos-carry-sched=always`), which the split does not carry ([`downstream/carry-sched-interaction.txt`](downstream/carry-sched-interaction.txt)).
    - With `-mos-carry-sched=off`, the change shrinks default code by 25,290 B, as it does in the split.
    - With the old 14 sets, carry scheduling saves 39,209 B of default code; with upstream's six sets it saves 492 B. The carry model's benefit rests on the sets derived from the native classes (`GPR_LSB_with_Ac16`, `Anyi1_with_Ac16` and the others), not on anything native.
    - Native growth is 1,638 B with carry scheduling off.
    - On an 11-input sample, the two compilers give identical code with MachineLICM, MachineSink and both schedulers disabled, so the change acts only through pressure.
