## Code review

**#627 separates graph operations from spilling policy.** The refactor exposes graph vertices and builder operations so another pass can use them. Saved-value state belongs to `MOSImagRegSpill`; it no longer lives in the graph builder. Vertex IDs remain stable until removal and are reused only after incident edges, retention state and register mapping are cleared. The builder uses existing live-register IDs when adding edges, avoiding insertion that could invalidate a vertex reference. These changes support reuse without intentionally changing spilling decisions.

**#628 consumes the spiller's feasibility guarantee.** Previously assigned neighbors contribute their actual occupied register units; unassigned neighbors contribute a conservative upper bound on blocked candidates. A vertex can be removed only when more candidates remain available than that bound. Reversing the removal order then guarantees at least one candidate when each removed vertex is assigned. The assignment step checks the union of neighboring physical register units, so a byte, its low bit and its containing pair cannot be treated as unrelated storage. Assignments are retained in `VirtRegMap` across successive instruction regions.

Early-clobber results are introduced before dying inputs leave the graph. Ordinary results are introduced after those inputs leave. This distinction matters for the scratch pair emitted by soft-stack transfers. Terminators are processed together, and the builder trims expired vertices after each region. The assignment pass changes allocation metadata while preserving the instruction stream and its liveness analyses.

The accepted input boundary comes from `MOSImagRegSpill`: one block without successors, restricted SSA operands, and no calls/regmasks, PHIs, parallel copies, inline assembly or constrained physical inputs. The assignment pass additionally accepts the subregister, `REG_SEQUENCE` and early-clobber forms produced by spill emission. Its direct `-run-pass` entry relies on that contract; it is not a general-purpose whole-function allocator.

## Executed checks

Current main and #627 passed 21 allocator checks each; #628 passed 39. The corresponding MOS CodeGen/MC suites passed 150, 150 and 153 tests, respectively, with one unsupported test in each run. All 34 cross-variant spill and undef streams were byte-identical. The 16 #628 instruction bodies matched after removing the `dead` annotation immediately preceding early-clobber scratch definitions; eight were not byte-identical before that normalization. The original comparison and the normalized comparison are both retained.

The first main allocator run exposed a checker assumption that a tied operand and a store must print a `killed` annotation. The checker was corrected to accept either spelling; the original checker and failed run remain in the evidence, and the full main allocator run was repeated successfully.

The retained pressure input loads 16 distinct volatile bytes, then stores them in a nonsequential order and its reverse. An independent interpreter follows its loads, stores, spill slots and assigned byte/pair locations, checks all 32 output events, and models early-clobber scratch writes before reading inputs. A separate liveness scan rejects overlapping assigned units for simultaneously live values. Neither checker uses the compiler's interference graph or its simplification result. A deliberately colliding assignment is rejected by a retained sensitivity check.

The mixed bit/byte/pair assignment tests also receive the independent overlap check. These checks establish the storage contract for the inspected MIR, not execution of final hardware instructions. The build is Release, assertions and LTO disabled, with the experimental allocator disabled by default. Assertion-enabled and cross-target suites were not rebuilt for this review; no runtime or performance claim is made.

## Useful feedback

The scoped tests support the spill refactor and the new assignment pass within their stated single-block boundary. Retain those guards while adding the downstream native/far register classes and hardware-allocation path. The early-clobber scratch requirement should remain explicit in assignment tests, since normal stack transfers use the scratch pair before consuming their inputs.

The next acceptance milestone is a working hardware allocator for the supported single-block subset, followed by executable value checks. Calls, control flow, undef groups and native/far classes need explicit contracts and tests before widening the current guards. Spill-cost and scratch-budget improvements remain separate profitability work; this review does not measure a speed or code-size benefit.
