# Patch 0031: reuse the destination of an earlier copy

Stacked on [patch 0030](0030-validation.md). Found during the
[independent review of 0030](0030-claude-review.md): the second reuse branch of
`MOSInstrInfo::getRegWithVal` was dead code, because the clobber map was
updated for a copy before the copy was inspected, so a copy's own destination
always looked clobbered.

## Change

`getRegWithVal` walks backwards from the insertion point. For every instruction
it first recorded which registers of the wanted class the instruction modifies,
then, if the instruction was a copy, checked whether that copy's destination
holds the value. A copy's own definition of its destination was therefore
already in the clobber map when the copy was checked, and
`Src == Val && RC.contains(Dst) && !Clobbered[Dst]` could never be true. The
first branch (`Dst == Val`, reuse `Src`) was unaffected, which is why the
existing `copy-phys-reg.mir` cases and the 0030 cases all pass either way.

The fix records a copy's definitions only after inspecting it. `ReuseReg`, which
0030 added to clear stale kill flags, additionally clears a `dead` flag on the
establishing copy, since reusing the destination keeps it alive. Both controls
(destination redefined, source redefined) are unchanged.

Upstream's own test `imag8_to_imag8_gpr_use` was written for exactly this reuse
(and its sibling `…_clobber_src` for the rejection), but its checks were
autogenerated from the buggy output and so expected the scavenged reload. They
are regenerated with `update_mir_test_checks.py`; that function's expectation
becomes `$rc1 = STImag8 $x` and nothing else in the file changes.

The typical change is the intended one: after `$y = LDImag8 $rcN`, a later
`$rcM = COPY $rcN` becomes `sty __rcM` instead of `ldx __rcN; stx __rcM`, and
after `$a = T_A $x` an X-to-Y copy becomes a single `TA`. The six pairs that
grow do so because the reused register's live range is now honestly longer, so
the scavenger hands a later temporary a different register (X instead of Y);
in `920506-1.c` a value that was previously derived in place by `dex` is then
materialised by `ldx #0`, one byte longer. None of those six executes more
instructions than before.
