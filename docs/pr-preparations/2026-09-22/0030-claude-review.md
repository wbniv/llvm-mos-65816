## The C++ change (0030)

`getRegWithVal` walks backwards from the copy being expanded looking for a
register of the wanted class that provably still holds the value: either the
copy that *defined* the value from such a register, or a copy that *stored* the
value into one. When it finds one it returns that register and the caller emits
a new use of it at the insertion point. Any `killed` flag on that register
between the establishing copy and the insertion point is now wrong, and the
verifier rejects the next use as undefined.

Codex's `ReuseReg` clears `killed` flags on the register (alias-aware, so the
`$ylsb` case is covered) over exactly `[establishing copy, insertion point)`.
That range is right at both ends: the establishing copy may itself carry the
kill (case `reuse_gpr_killed_by_copy`), and the instruction at the insertion
point is the pseudo about to be deleted. A register redefined inside the range
is never reused (the `Clobbered` map), so there is no other live segment whose
kill could be wrongly removed. The sibling helper `isCopyRedundant` already
follows the same clear-kills discipline. It does not add a kill at the new use;
post-RA kill flags are optional, so that is a precision loss, not a bug, and
the corpus shows it changes nothing.

**Repeated reuse.** A value can be reused twice (`$rc6 = COPY $rc4` and later
`$rc7 = COPY $rc4`, both becoming stores from `$y`). The second reuse's range
includes the first reused store, and the baseline produces two verifier errors
for it. Added as case six of the test; it passes.

**What was wrong next to it.** The loop recorded each instruction's clobbers
*before* inspecting it as a copy, so a copy's own destination was always
"clobbered" and the `Src == Val` branch could never return. That is not a
liveness bug, it is a missed optimization: after `$y = LDImag8 $rc4`, a later
`$rc6 = COPY $rc4` was lowered as a scavenged `LDImag8` plus `STImag8` instead
of `STImag8 $y`. Upstream's own `copy-phys-reg.mir` has a function named
`imag8_to_imag8_gpr_use` for exactly this reuse (and `…_clobber_src` for the
rejection), with checks autogenerated from the buggy output. Fixed in 0031.

## The tests (0030)

Five well-chosen shapes plus the repeated-reuse case: Y reuse across an indexed
load's kill, A reuse across a store's kill, an overlapping sub-register kill, a
kill on the establishing copy, a clobbered-value control that must keep its
kill and reload, and the double reuse. Each of the positive cases fails on the
unpatched compiler (verifier or FileCheck) and the control passes on both,
which is the right shape for a regression test.

## Validation (0030)

Codex's record was already honest and mostly complete (isolated assertion
build, 84 MOS CodeGen tests, six-level C matrix, assembly identical with and
without the fix). What it lacked was breadth beyond one C file, which matters
for a change that runs on every post-RA copy. The gcc `c-torture/execute`
corpus was compiled to IR by the pinned upstream Clang (1,390 of the 1,656
files in that directory; the other 266 need headers or features that Clang
rejects) and pushed through the
unpatched and the 0030 `llc` at `-O0`, `-O2` and `-Os` with MachineVerifier:

| Outcome | Count |
|---|---|
| Rejected by the unpatched backend with `Using an undefined physical register`, accepted with 0030 | 20 (18 files at `-O0`; `pr53645-2.c` at `-O2` and `-Os` as well) |
| Accepted by both, assembly identical | 4,070 (every such pair) |
| Fail on both (76 pairs; 4,170 comparisons in total) | 76, of which `strlen-4.c` at `-O0` fails differently on each side: `PH $p` undefined on the baseline, `assertNZDeadAt` on the assertion-enabled candidate; both are the same pre-existing status-register liveness bug, and the assertion reproduces on a pristine assertion build |
| Fail only on the (assertion-enabled) patched build | 4, all pre-existing: `Remaining virtual register` in `bitops-1.c` (`-O2`, `-Os`), `pr91450-1.c` and `pr91450-2.c` (`-O0`) reproduces on a pristine assertion build; the unpatched reference has assertions off and cannot see it |

So the bug is not rare at `-O0`, the fix repairs every instance the corpus
reaches, and it changes no generated code anywhere. MC/MOS passes (46) on the
standalone 0030-only binary (Codex's rerun; my own MC run used the stacked
0030+0031 build and is evidence for that build only).
