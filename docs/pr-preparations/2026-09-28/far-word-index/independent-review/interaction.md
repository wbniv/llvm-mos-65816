## Actionable validation issue

### REVIEW-INTERACTION-01 — P2: 0069's checks accept the wrong addressing opcode

**Location:** [far-loop-range.mir:11](/tmp/far-word-independent-review-source/far-loop-range.mir:11), [far-loop-range.mir:171](/tmp/far-word-independent-review-source/far-loop-range.mir:171), and the analogous checks throughout that file; the corresponding patch starts these checks at `0069-mos-far-loop-range.patch:163`.

Every expected byte opcode in this file ends with an ordinary trailing space. Under the RUN lines' FileCheck options, [Pattern::parsePattern:810](/home/will/llvm-mos-65816/vendor/llvm-mos/llvm/lib/FileCheck/FileCheck.cpp:810) strips trailing spaces and tabs. The resulting pattern has no regex and becomes a fixed substring at line 840; the matcher uses `Buffer.find(FixedStr)` at line 1134. Consequently:

- `= G_LOAD_FAR_INDIR ` also matches `= G_LOAD_FAR_INDIR_IDX` and `= G_LOAD_FAR_INDIR_IDX16`.
- `= G_LOAD_FAR_INDIR_IDX ` also matches `= G_LOAD_FAR_INDIR_IDX16`.

**Concrete valid input:** the existing `offset_256` fixture has an i8 induction from zero through 248 and adds displacement eight. Its final access needs offset 256, so A16 must keep the explicit pointer. An erroneous Y8 indexed load for that same fixture would still satisfy its A16 check at line 172. The existing `wrapped_induction`, `full_cycle`, wrong-flag, wrong-branch, and other negative cases have the same weakness. The OFF checks do not establish that disabling the new proof restores the unindexed opcode. Positive Y8 checks in XY16 mode do not distinguish Y8 from Y16 selection.

**Action:** terminate every expected opcode with an explicit regex whitespace boundary, for example `G_LOAD_FAR_INDIR{{ }}` and `G_LOAD_FAR_INDIR_IDX{{ }}`, or check the following operand/type. Add a sensitivity check for the wrong opcode when tests are next authorized. The 0070 file already uses the explicit boundary for its unindexed word expectations, e.g. [far-word-policy.mir:192](/tmp/far-word-independent-review-source/far-word-policy.mir:192).

**Confidence and classification:** high confidence from FileCheck's implementation; no execution was needed for this inference. This is a regression-check defect, not evidence that the compiler currently emits the wrong opcode. The retained statement that all 78 case/configuration checks pass must be read with this limitation.

**Prior-work reconciliation:** searched the structured defect records, current investigations/plans/TODO/upstream summary, patch contents, and history for FileCheck/opcode-boundary/prefix/whitespace and the far-loop test. No canonical compiler defect for this test issue was found. The 0070 test generator explicitly adds `{{ }}` to word fallback checks; that change does not update 0069. The live test and standalone 0069 patch both retain the weak checks. No compiler defect record or status change is warranted from this static validation finding alone.

## Coverage gaps worth addressing

1. **Check operand dataflow and both siblings in the new MIR tests.** The 0070 mixed cases at [line 356](/tmp/far-word-independent-review-source/far-word-policy.mir:356) check only the word opcode. They are useful: reversing instruction order changes visitation order, and the negative word expectation can catch the unsafe group limit change. They do not directly establish the byte sibling's chosen form, shared original base, computed index, preserved memory size, or disappearance of the wide pointer add. A type-correct but wrong base/index would pass these opcode checks and the machine verifier. This is a coverage recommendation; the implementation I inspected supplies the correct operands.

2. **Preserve a compact word integration regression alongside the policy MIR.** The new word MIR cases all start from the same s8 loop, use an already-lowered SBC condition, and keep their otherwise unused loads alive with `volatile`. The retained C bounds/pressure/Farblit runs cover live result consumption, generic lowering, mode changes, and bank crossing, while `0062` has an LLVM IR constant-displacement word test. A small IR test using a runtime base and a known-bits bounded offset such as `2 * (index & 127)`, with a live native-word consumer, would independently exercise 0070 without needing 0069's loop matcher. This is a missing narrow regression boundary, not a demonstrated failure or a claim that integration evidence is absent.
