## Contracts checked

- **Flag semantics.** In a MOS address space 0 GEP, the index width equals the 16-bit pointer width. For `getelementptr i8, ptr B, i16 I`, the offset is `I` itself, with no scaling or extension. LangRef `nuw` requires only that the unsigned sum `B + I` does not wrap. Because `I < 2^16`, the sum wraps exactly when the result is below `B` unsigned. Both proof paths establish `result uge B`. Path (a) uses a `nuw` AddRec starting at `SCEV(B)`, which is non-decreasing in unsigned order for any step and any affine or non-affine shape. Path (b) uses `SE.isKnownPredicate(ICMP_UGE, result, B)`. The filters in `MOSRecoverNearNoWrap.cpp:65-69` restrict the pass to exactly this shape: scalar pointer, address space 0, `i8` element, one `i16` index. Probes confirm that vector, address space 1, `i16`/struct element and `i8`-index GEPs are skipped.
- **Validity of the SCEV facts.** The pass is a refinement of the *source* program, not of LSR's output taken in isolation. The facts come from the pre-LSR IR: for example, `{%src,+,1}<nuw>` is inferred from the original `inbounds` GEP through `isSCEVExprNeverPoison`. The node survives in LSR's preserved ScalarEvolution. Recomputing SCEV from the post-LSR IR yields only `<nw>`: `opt -passes='loop-mssa(loop-reduce),print<scalar-evolution>'` shows `{%dst,+,1}<nw>` for the unflagged control. In every execution where the source is well defined, the AddRec does not wrap on any iteration that runs. The new GEP computes the same value on those iterations, so it produces no new poison. LSR relies on the same principle: with recovery disabled, SCEVExpander emits `getelementptr nuw i8, ptr %p, i16 5` from `(5 + %p)<nuw>` (probe p06). Conditional uses do not leak flags. A conditionally executed `inbounds` access, a conditional-only flagged twin, and an access after an early exit all stay unflagged (probe p05), because SCEV's never-poison inference requires execution on every iteration. The same holds for invariant starts: SCEV propagates start flags only when `getDefiningScopeBound` reaches the loop header.
- **Use-specific SCEV flags** (`SCEVUseT`, `ScalarEvolution.h:122-237`). `getSCEV` returns a bare `const SCEV *`. `SCEVNAryExpr::hasNoUnsignedWrap()` reads only the node's own `SubclassData` and never reads use flags. `AR->getStart() == Base` compares opaque values, so a start that carries use flags never equals `Base`. No producer in this tree sets use flags (a grep for `getUseNoWrapFlags`/`hasUseFlags` finds only the header). If use flags do start being produced, facts that move from nodes onto uses become invisible to this pass. Coverage would shrink, but no unsound fact would become visible. The range-based AddRec NUW inference (`ScalarEvolution.cpp:6843-6847`, `getRangeForAffineAR`) is bounded by the constant maximum backedge-taken count. It is therefore valid on every executed iteration, and probe p11 shows it proving 0xFF00+63 while refusing 0xFFF0+63.
- **Pipeline.** `-debug-pass=Structure` shows the pass inside LSR's Loop Pass Manager, directly after LSR. `skipLoop` covers optnone functions and opt-bisect (the p12 optnone function is not flagged). At `-O0` and with `-disable-lsr`, LSR is never added, so the inserted pass never runs (0 pass lines). `setPreservesAll()` is acceptable: adding `nuw` removes no CFG, loop or SCEV fact, and cached SCEVs for the flagged GEPs become conservative rather than wrong. The legacy pass name no longer collides with the `cl::opt`, which the `opt` startup check confirms.
- **Consumption.** `IRTranslator::translateGetElementPtr` copies the GEP's `nuw` onto the single `G_PTR_ADD` (element size 1, so no `G_MUL`). The flag's only MOS consumer is `canFoldNearIndex` (`MOSLegalizerInfo.cpp:2297-2310`), which takes it as proof that the 24-bit `DBR:base + index` does not carry into the next bank. The peel loops check every `G_PTR_ADD` they fold. Reassociating a chain in which every link is `nuw` is safe because every partial sum is bounded by the non-wrapping total (probe p06: `ldy #5` with `(zp),y`). Outside 65816, `canFoldNearIndex` already returns true, so the `hasW65816` gate changes only IR (the `PLAIN` check).

## Findings

1. ~~**Nonblocking, fix before posting: the pass instance leaks when LSR is not scheduled.**~~ Resolved in `43e1c4d6` (see Re-review). `MOSTargetMachine.cpp:249-250` hands `insertPass` a live instance. `TargetPassConfig` adds that instance only after LSR is added, and `~TargetPassConfig` deletes only `Impl`, which holds a raw `IdentifyingPassPtr`. Under gdb, `createMOSRecoverNearNoWrapPass` against `~MOSRecoverNearNoWrap` counts are: `-O0` 1 created, 0 destroyed; `-disable-lsr` 1 created, 0 destroyed; `-O2` 1 created, 1 destroyed. A `-start-after` past LSR leaks the same way. This is the only instance-based `insertPass` in `llvm/lib/Target`. A LeakSanitizer build would report it on every MOS `-O0` compile. Suggested fix: export `char &llvm::MOSRecoverNearNoWrapID = MOSRecoverNearNoWrap::ID;` from the header and call `insertPass(LSR->getPassID(), &MOSRecoverNearNoWrapID)`. `TargetPassConfig` then creates the pass through `Pass::createPass` only when LSR is added. Rejected alternative: calling `addPass` after `TargetPassConfig::addIRPasses()`. That runs outside LSR's Loop Pass Manager, where SCEV has already been recomputed and the recovered facts are lost.
2. ~~**Nonblocking: the `isKnownPredicate` branch has no regression coverage.**~~ Resolved in `43e1c4d6` (see Re-review). Every function the test flags goes through path (a) (`{%src,+,1}<nuw>`, `{%dst,+,1}<nuw>`, `{@buf,+,1}<nuw>`). Deleting or corrupting `MOSRecoverNearNoWrap.cpp:81-82` would leave the test green. ## Limits

- No LLVM rebuild, so findings 1 and 2 are backed by code reading, gdb counts and SCEV dumps rather than rebuilt fixes.
- No runtime or differential check (MAME or bsnes-jg) was run on probe assembly, and the downstream runtime evidence was not replayed. Soundness rests on the LangRef and SCEV argument plus IR inspection.
- The review did not audit SCEV's own flag inference (`isSCEVExprNeverPoison`, `getDefiningScopeBound`, range sharpening) beyond reading the relevant code. The pass is exactly as sound as ScalarEvolution's no-wrap flags, the same trust LSR and SCEVExpander place in them.
- Upstream commit `86ab6d6e2ecf` could not be inspected, because the source checkout's history is shallow (6 commits). The use-flag analysis is based on the tree's code.
- `-start-before=mos-near-nowrap-recovery` never starts the pipeline, because inserted passes are added only after their anchor pass. The AsmPrinter then asserts. This is inherent to `insertPass`, so it is not listed as a finding. Isolated pass tests are impossible anyway, because the pass depends on LSR's warm ScalarEvolution.
- `run-suite.sh` overwrites `build/near-proof-upstream/candidate-suite.json`. The reviewer's run is kept as `build/near-proof-upstream/review/suite-candidate.json`, and the coordinator's file was restored byte-for-byte.

### (b) `mos-xy16-preserve-x-p-save`: falsification attempts

The claim survives, and the evidence is stronger than the record states.

- **No patch 2 code is needed.** On boids, the post-recovery IR with recovery on differs from recovery off only in 80 lines: 40 GEPs gain `nuw`, and no other difference exists. With recovery disabled, the candidate's assembly is byte-identical to the patch-1-only compiler's. Feeding the recovered IR to the **patch-1-only** llc b8006489… with `-start-after=loop-reduce` reproduces the identical failure (`main`, `%bb.25`, `PH $p`, "Using an undefined physical register"), with and without `-disable-spill-hoist`. There, no patch-2 code executes; only its 40 IR flags are present. The recovery-off IR through the same command passes. The **downstream** toolchain `build/llvm-mos/bin/llc` (cf5355d3…) fails identically on that IR. So the latent defect is present in the project's own compiler too, not only in the extracted prerequisite. The record says it was "not reproduced by any census input on the downstream compiler". That remains true for source inputs, but the backend defect is demonstrably reachable there. I recommend adding both reproductions to the record.
- **The failure is isolated to the REP/SEP pass.** The candidate's MIR at `-stop-before=mos-insert-rep-sep` passes the verifier. Round-tripping that MIR needs `stack-id: mos-static` rewritten to `default`, because MIR parsing rejects the MOS stack ID: "StackID is not supported by target", a separate serialization gap. After that rewrite, it re-verifies clean under `-run-pass=machineverifier`. `-run-pass=mos-insert-rep-sep -verify-machineinstrs` then fails with the same `PH $p` error. Valid input goes in and invalid output comes out, so the verifier violation is created inside `MOSInsertREPSEP`. `git blame` attributes `SaveAP`/`PLive` to patch 1.
- **The `$nz` live-ins come only from the whole-`$p` read.** A scan of `main` for non-`undef` reads of `$p`, `$nz`, `$n` or `$z` finds exactly one, `PH $p` in `%bb.28`, both after prolog-epilog and before `mos-copy-opt`. With recovery off there is no such `PH $p` and no N/Z live-in. The later increase to 19 blocks comes from post-RA branch expansion splitting those same blocks. The whole-`$p` read is justified by C: `%bb.27` ends with `GBR …, implicit-def $c` and `%bb.28` executes `ADCImm …, $c`. `%bb.25` itself has no N/Z live-in, because its `JSR __mulhi3` register mask ends backward liveness.
