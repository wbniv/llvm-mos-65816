[MOS] Add the far address space and allocate Imag32 quads on the 65816

Add address space 2 for far data pointers: `p2:32:8` in the MOS data layout (TargetDataLayout and MOSTargetMachine) and AS_Far in MOS::AddressSpace. A far pointer is a 32-bit value whose low three bytes are the 65816 long address; 32 bits keep it a simple MVT, since there is no MVT::i24.

A runtime far pointer lives in an Imag32 quad, the RL register family of the previous commit (llvm-mos#594). This commit adds Imag32 to the register bank and makes the class allocatable where MOSSubtarget::hasAllocatableImag32() holds. A quad is usable only if the linker keeps its four RS bytes contiguous, which no platform contract states yet. The 65816 needs quads for far data, so the predicate is the 65816 for now. On every other CPU Imag32 has an empty allocation order (an alternative order selected by the predicate), so a quad virtual register fails to allocate with a clear error. The quads are not reserved there, because call lowering treats reserved registers and all of their aliases as unavailable for arguments, which would move byte and pointer arguments out of the RS pairs the quads cover. The predicate is the one place to switch to a platform contiguity contract. A strong copy hint that is not in the allocation order is no longer offered to the allocator; the allocator asserts on such hints.

Calls: where quads are allocatable, a far pointer argument is assigned to RL1-RL3; a far pointer that finds no free quad, and every far pointer on other CPUs, goes to a 4-byte stack slot. It never falls through to the generic pointer rule, whose 16-bit RS pair cannot hold it. The calling-convention type of a far pointer is i32, and incoming 32-bit values are accepted.

Address space 2 changes meaning on every MOS CPU. Upstream has no p2 entry in the data layout, so an addrspace(2) pointer there is a 16-bit pointer like any other. With this commit it is a 32-bit far pointer on every MOS CPU, not only the 65816: IR that used addrspace(2) for some other purpose now gets 32-bit pointers, and on CPUs without the 65816 the next commit rejects far accesses and far pointer values with far-specific errors.

Default-mode effect: the data layout string gains p2:32:8 for every MOS CPU. Generated code for the fixed input set is identical on all 14 MOS CPUs (assembly and objects). On mosspc700, 18 corpus inputs that already abort upstream in the greedy allocator ("Target hint is outside allocation order", record mos-spc700-hint-outside-order) fail differently: the strong-hint filter turns the assertion into "ran out of registers during register allocation" followed by an abort in the virtual register rewriter.

Tests: imag32-allocation-gate.mir checks that the 65816 allocates a quad and that mos6502 reports that no register is available, with no hint from a quad outside the order; it replaces #594's imag32-nonalloc.mir, whose non-allocatable class this commit changes. far-ptr-arg-exhaustion.ll checks call lowering for a fourth far pointer and for near/far interleavings in plain mosw65816, +mos-a16 and +mos-a16,+mos-xy16, and that mos6502 passes every far pointer on the stack. Nothing produces address space 2 values until the next commits.

Validate: `build/bin/llvm-lit -v llvm/test/CodeGen/MOS/imag32-allocation-gate.mir llvm/test/CodeGen/MOS/far-ptr-arg-exhaustion.ll`.
