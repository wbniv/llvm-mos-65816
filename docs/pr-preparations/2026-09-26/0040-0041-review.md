## 0040: correctness, venue and test extraction

The guard is conservative and correctly precedes both instruction removal and
`rmFromMergeableSpills`. `all_defs()` identifies every register definition;
an additional virtual def prevents coalescing while physical defs and the
spilled register's own definition preserve existing behavior. The rejected
access continues through normal `spillAroundUses` processing. Deleting only
the interval is not an equivalent repair because InlineSpiller cannot unassign
an already allocated scratch interval from LiveRegMatrix.

The source-only adaptation keeps the exact predicate and changes only the
comment to a short present-tense lifetime invariant. Current LLVM also has
`getVDefInterval`; the old draft's universal statement that upstream never
creates such intervals should not be repeated. The evidenced submission venue
is nevertheless **llvm-mos**, because the retained causal regression is MOS.
No tested LLVM-target reproducer is claimed.

Fresh tests confirmed an important qualification in the old validation:
the original `.ll` fails for the correct reason on preserved pre0040 binaries,
but not directly on current MOS with spill hoisting disabled. With hoisting
enabled, current MOS instead hits the distinct 0033 remaining-vreg failure.
That is not a current causal red for 0040.

To pin the relevant pressure shape, the same original IR was translated with
the retained pre0040 compiler to `-stop-before=greedy` MIR. That MIR replays on
current stock MOS and reproduces the exact
`SplitEditor::enterIntvAfter` / `MI && "enterIntvAfter called with invalid index"`
assertion even with `-disable-spill-hoist`. It uses no native-width feature
attribute or downstream-only opcode. The packet removes absolute path metadata,
normalizes trailing whitespace, and adds contract comments and two RUN lines;
it does not change the machine instructions or invent MIR properties.

The exact packet input passes standalone MachineVerifier on all three binaries
below. Both its greedy-only and full-pipeline RUNs fail on the preserved old
baseline and pristine current main; both pass with the preserved old 0040
compiler, including the full-pipeline FileCheck. Thus the new fixture is valid
at its pass entry and distinguishes the intended defect, unlike a test that
merely trips an unrelated pass precondition.

Destination/base: llvm-mos main
`7bd67c0ae4e8bb65a3f980912bf201df22131e34`. No candidate prerequisite: 0033 is
avoided by test configuration, and #320/#321/SNES extraction is irrelevant.
The 1,335-line fixture retains substantial allocator pressure; further size
reduction is desirable but not necessary for its validity. The predicate has
no identified correctness blocker. The exact-current gate subsequently passed
as recorded below; retained old green is not substituted for current green.

## 0041: correctness and required LLVM adaptation

Reviewed the split and merge helpers, width checks, matching operand-group
walk, per-register ties, physical-def class handling, and plain input/output
paths against current InlineAsmLowering and SelectionDAG's part conversion.
The helpers consistently use least-significant piece first; each tied input
is allocated in the output's selected class and tied at the correct operand
index. Using shifts avoids reliance on unselected scalar unmerge operations.

The old generic patch cannot simply be reanchored onto LLVM. MOS has a scalar
result **zero-extension** branch that LLVM lacks; AArch64's `i128` `r` operand
selects two GPR32 pieces, so the merged width is only 64 bits. Without a new
extension branch, the candidate would still reject every direct `i128` output.
This dependency is not supplied by the standalone 0037 extraction.

The packet adds precisely this branch after merge/truncate:

```cpp
} else if (OpInfo.Regs.size() > 1 && ResTy.isScalar() &&
           ResTy.getSizeInBits() > SrcSize) {
  MIRBuilder.buildAnyExt(ResRegs[i], SrcReg);
```

The value is already a typed scalar generic register from `buildMergeFromAsmRegs`.
`G_ANYEXT` matches current SelectionDAGBuilder's `getCopyFromParts` integer
widening contract (around lines 278–285 of pinned LLVM), whereas MOS's existing
`G_ZEXT` selects a particular permitted value for the otherwise undefined high
bits. Single-register behavior is unchanged. This is an explicit extraction
adaptation requiring new validation, not an assertion of source or assembly
identity with the old compiler.

Other LLVM context differences are removed rather than importing MOS APIs:
the current `getNumRegisters` call is preserved, MOS's diagnostic comment around
the tied assertion is absent, and there are no 0037 indirect-output edits.
Thus the destination is **llvm/llvm-project** main
`e59a0c697552ae7d1c3aeed5774e829cdc5e16b5`, standalone. MOS can backport it
separately using MOS's register-count hook; neither native-width nor far-memory
work is required to submit the generic direct-operand repair.

The packet test explicitly checks `G_ANYEXT` after every merged output, with
MachineVerifier at both `-O0` and `-O2`, plus full codegen without fallback.
It preserves the earlier O0-only assembly expectations. A fresh experiment
running those old assembly expectations at O2 fails because register/assembly
choices differ; O2 codegen itself succeeds. That exploratory FileCheck failure
is retained, not counted as a compiler regression or a green run.
`build-pair-isel.ll` retains its existing SelectionDAG checks with an explicit
selector flag and adds a GlobalISel no-fallback codegen check. It does not pin
MOS's old zero-filled upper bits in an LLVM undefined-high-bits result.

Do not repeat the original blanket assertion that every unsupported shape
now safely diagnoses. The tied path retains a single-source-vreg assertion,
output handling is not a blanket scalar-only precheck, and register allocation
still has the independent bounds issue owned by 0056. The new split helper
does reject non-scalar inputs and both helpers reject big-endian/mixed-width
groups. AArch64 big-endian already bails in IRTranslator, so it would not be a
direct test of this helper guard. Exploratory `<4 x i64>` `w`-constraint probes
were rejected by the target before these helpers and establish no new coverage.
No new defect is alleged from those probes.

Source review approves the scoped direct-scalar algorithm and documented
LLVM adaptation, **conditional on exact-package current-base build/tests**.
That is the remaining substantive readiness gate, not a merge dependency.
